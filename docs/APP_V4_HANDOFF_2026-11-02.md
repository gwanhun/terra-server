## 1. 앱에서 할 일

| # | 항목 | 할 일 | 필요 시점 |
|:---:|---|---|---|
| ① | `alerts` 에 `env_temp_high` / `env_temp_low` / `env_humid_low` / `env_humid_high` 가 생김 | 실시간 상태 칩·알림 목록 표시 (`message` 의 `[ ]` 안 문구 = 상태 칩) | 1단계 전 |
| ② | 푸시 이벤트 `env.alert.triggered` (`phase` started / reminder) | Edge Function 수신부에 type 추가, `payload.title` 을 그대로 쓸지 결정, 푸시 수신 OFF 사용자 거르기 | 2단계 전 |
| ③ | `env_daily_reports` (기기 × 날짜) | 일일 분석 화면: `temp_card` / `humid_card` 의 `title` + `lines` 표시, `null` 이면 빈 상태 | 3단계 전 |
| ④ | `env_weekly_reports` (기기 × 주) | 주간 분석 화면: 카드 + `notices`(데이터 부족·수집 불안정 안내) | 3단계 전 |
| ⑤ | 목표 온습도 설정 범위 변경 | 온도 MIN/MAX 15~29℃ **0.5 단위**, 습도 35~85% **5 단위**, MIN < MAX(같으면 400). 이 범위 밖 값을 보내지 않는지 확인 | 서버 반영 전 |

- 카드·알림 문구는 서버가 기획 원문대로 완성해서 저장합니다. 앱에서 문구를 조합할 필요는 없습니다.
- 카드 `status` 는 `danger` / `caution` / `normal` 입니다. `alerts.severity` 의 `warning`(=주의) / `critical`(=경고)과 **다른 어휘**입니다.
- 세 테이블(`alerts`, `env_daily_reports`, `env_weekly_reports`) 모두 RLS 로 본인 기기 행만 읽히고 Realtime 구독이 됩니다. 분석 테이블은 **이미 운영 DB 에 만들어 두었습니다**(비어 있음).

## 2. 켜는 순서

| 단계 | 서버 | 앱에서 보이는 변화 | 필요한 회신 |
|---|---|---|---|
| 0 | 배포(모든 스위치 꺼짐) | 없음 | — |
| 1 | 실시간 판정 켬 | `env_*` alerts 가 Realtime 으로 들어옴. 구 판정 `temp_high`/`temp_low`/`humid_low` 는 더 안 생김. 푸시 없음 | ① 준비 완료 |
| 2 | 푸시 켬 | `env.alert.triggered` 수신 시작 | ② 준비 완료 |
| 3 | 분석 리포트 켬 | 1단계를 켠 **다음 날** 아침부터 일일 카드, 그 다음 **온전한 한 주**가 끝난 월요일부터 주간 카드 | ③④ 준비 완료 |
| — | 설정 범위 검증 반영(별도 배포) | 범위 밖 PATCH 가 400 | ⑤ 확인 |

분석 리포트는 실시간 판정을 켜기 전 구간을 "이벤트 없음"으로 잘못 보여 주지 않도록, 켠 시각 이후에 시작하는 날·주만 만듭니다.

## 3. 생성 시각

| 리포트 | 집계 구간(KST) | 생성 |
|---|---|---|
| 일일 | 전날 08:00 ~ 당일 08:00 | 08시대 1차, 09:05 이후 내용이 바뀐 기기만 1회 갱신(`pass` 2) |
| 주간 | 지난주 월 08:00 ~ 이번 주 월 08:00 | 월 09:05 이후 1회 (서버가 멈춰 있었으면 그 주 안에 복구) |

09:05 까지 기다리는 이유: 08시 직전에 시작한 이벤트는 유지 시간(2분, 과습은 1시간)이 지나야 기록되므로, 08:00 정각에 만들면 빠집니다.

## 4. 회신 부탁

1. ①~④ 각각 준비되는 시점(단계별로 켜겠습니다)
2. ② 푸시 문구: 서버 `payload.title` 을 그대로 쓸지, 앱에서 `kind`·`level`·`value`·`threshold` 로 조합할지
3. ② 푸시 수신 OFF 처리: 앱 Edge Function 에서 거르는 걸로 괜찮은지(서버는 항상 적재)
4. ⑤ 지금 앱이 0.1℃ 단위나 MIN = MAX 를 보내는 화면이 있는지
