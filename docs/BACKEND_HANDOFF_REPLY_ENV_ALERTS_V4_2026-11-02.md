## 1. Q1 — 온도 보정 "끔"과 기본 −1.5℃

### 1.1 −1.5℃는 공장 보정입니다

- 기기(ESP32-S3) 보드가 스스로 내는 열 때문에 옆의 DHT22 가 실제보다 높게 읽혀서, 펌웨어 빌드 기본값 `CONFIG_APP_TEMP_OFFSET_MDEG` = −1.5℃로 깎아서 보냅니다(`specs/stage-k-unified-hub.md` R12 "S3 기기 보드 발열 기준").
- 기기는 사용자가 따로 보정한 적이 없으면 이 값을 씁니다. NVS(`terra/t_off`)에 값이 있으면 그 값 **하나**만 씁니다. 기본값에 더하는 구조가 아니라 **덮어쓰는** 구조입니다.
- 운영 현황(2026-11-02, 활성 기기 23대): `temp_offset_c` = −1.5 19대 / −3.0 1대(운영 콘솔로 조정) / 미보고 3대(구 펌웨어).

### 1.2 그래서 앱 계산은 이렇게 해 주세요

기기에는 값이 하나뿐이라, 앱이 "공장 보정 −1.5 + 사용자 보정"으로 나눠서 보여 주고 보낼 때 합쳐야 합니다.

| 앱 동작 | 기기에 보낼 `offset_c` | 예 |
|---|---|---|
| 보정 끔 | **−1.5** | — |
| 더하기 1.0 | −1.5 + 1.0 = **−0.5** | |
| 빼기 0.5 | −1.5 − 0.5 = **−2.0** | |

| `devices.temp_offset_c` | 앱 화면 |
|---|---|
| −1.5 | 보정 꺼짐 |
| −0.5 | 켜짐 · 더하기 1.0 |
| −3.0 | 켜짐 · 빼기 1.5 |
| `null` | 구 펌웨어 — 현재값을 모름. 보정 화면은 막거나 "기기 업데이트 필요"로 |

- 화면의 크기 0.1~4.0℃ 범위면 기기에 가는 값은 −5.5 ~ +2.5℃ 라 서버 검증(±10℃)과 펌웨어 범위 안입니다.
- **"끔"에 0을 보내면 안 되는 이유**: 보드 발열이 그대로 실려 온도가 약 1.5℃ 높게 올라옵니다. v4 실시간 판정은 이 보정된 값으로 경고(29℃ 초과)·주의(MAX 초과)를 가리므로, 실제로는 27.6℃인 사육장이 29.1℃로 읽혀 **위험 경고 푸시가 잘못 나갈 수 있습니다.**
- 앱 임시 결정(끔 = 0 전송, `temp_offset_c == 0` 일 때만 "꺼짐")은 위 표로 바꿔 주세요. 말씀대로 "기기에 보낼 값" 계산 한 곳과 화면 표시 한 곳이면 됩니다.
- −1.5 는 앱 상수로 두면 됩니다. 나중에 보드별로 공장 보정이 달라지면(예: Terra Hub 는 발열이 더 커서 값이 다를 수 있음) 서버가 `devices.capabilities` 에 기기별 기본값을 실어 드리는 쪽으로 따로 알려 드릴게요. 지금 운영 중인 기기는 전부 −1.5 기준입니다.

## 2. Q2 — 앱의 `POST /devices/{id}/commands` 사용

- **사용자 JWT 로 써도 됩니다.** "운영 콘솔 대행용"이라고 적은 건 이 엔드포인트가 생긴 계기일 뿐이고, 일반 JWT 도 똑같이 받습니다. 본인 기기(해제되지 않은 기기)가 아니면 404.
- **빈도 제한 없음.** 다만 연타하면 명령이 그대로 여러 번 나가니 저장 버튼은 앱에서 한 번만 보내 주세요.
- 서버 검증은 `offset_c` 숫자·±10℃ 뿐입니다(위반 시 400). 공장 보정 합산은 앱 몫입니다(§1.2).
- **응답 시간**: 디스패처가 1초 주기로 발행 → 기기 적용 → 다음 telemetry(3초 주기)에 `temp_offset_c` 보고 → `devices.temp_offset_c` 갱신. 보통 **5초 안**이라 15초 대기면 충분합니다.
- **기기가 오프라인이면**: 명령 유효시간이 10초라 그 뒤 `status = no_ack`(발행했는데 응답 없음) 또는 `expired`(발행 전에 시간 초과)로 끝나고 값은 안 바뀝니다. 15초 대기 실패 시 `GET /devices/{id}/commands/{command_id}` 로 `status` 를 보고 "기기가 응답하지 않아요"를 구분해 보여 주면 좋습니다.
- **구 펌웨어(`temp_offset_c` = null, 3대)**: 기기가 값을 보고하지 않아 `devices.temp_offset_c` 가 바뀌지 않습니다. 이 기기는 명령 `status = acked`, `result = ok` 로 저장 완료를 판정해야 합니다(§1.2 표처럼 보정 화면을 막는다면 해당 없음).
- 보정을 바꾸면 그 순간부터 실시간 판정·분석에 쓰이는 온도가 바뀝니다. 서버 판정은 기기가 보낸 보정 후 값만 봅니다.

## 3. Q3 — 자동 환기·자동 분무

- **서버·펌웨어 모두 계획이 없습니다.** v4 기획(노션 "v4. 최종 정리 중")의 서버 범위는 판정·알림·분석까지이고, 기기를 자동으로 켜고 끄는 제어는 들어 있지 않습니다.
- 지금 있는 가장 가까운 기능은 **예약 가드**입니다(`schedules.guard`, 2026-09-16). 예약 분무·환기가 조건(예: 습도 이미 높음)에 맞으면 실행을 건너뛰고 `device.action.skipped` 를 보냅니다. 조건을 보고 기기를 **켜는** 기능은 아닙니다.
- 자동 제어가 생기면 정할 게 많아서(펌웨어에서 할지 서버에서 할지, 분무 펌프가 막혔을 때 반복 분무 방지, 예약과 겹칠 때 우선순위, 사용자 수동 조작과의 관계) 기획부터 따로 잡아야 합니다. 그때까지 토글을 만들지 않는 앱 결정이 맞습니다. 계획이 생기면 계약 문서로 먼저 알려 드릴게요.

## 5. 앱 회신(2026-11-03, 앱 §5) 확인

0.166.0 반영 내용 확인했어요. 보정 계산(공장 보정 −1.5 기준)과 저장 확인 흐름 모두 서버 기준과 맞아요.

1. **1단계(`ALERTS_V4_ENABLED`)와 #29(설정 범위 검증)를 서버 담당께 요청했어요.** 배포 후 실시간 판정이 실제로 켜지면 켠 시각(`ALERTS_V4_SINCE`)과 함께 알려 드릴게요. 그 시각부터 `alerts` 에 `env_*` 행이 쌓여요. 2단계(푸시)는 앱 "켜도 됨" 회신을 기다릴게요.
2. **일일·주간 카드의 하루 경계는 08:00~08:00(KST) 고정이에요.** 기획 0-1 의 집계 기준이라 서버가 자정으로 바꿀 수 없어요. 카드 행에 구간이 같이 들어 있으니 표시는 그 값을 쓰시면 돼요.
   - 일일: `report_date`(구간 시작일), `window_start` / `window_end` — 예: `report_date = 2026-11-02` → 11/2 08:00 ~ 11/3 08:00
   - 주간: `week_start`(월요일), `window_start` / `window_end` — UI 표시 기간은 기획대로 월~일

   온습도 상세 화면의 자정 단위 페이징과는 별개예요. 카드를 상세 그래프로 연결할 때는 `window_start` ~ `window_end` 구간을 열면 카드 내용과 정확히 맞아요.
3. (참고) 명령 상태에 `lost` 는 없어요. 서버가 쓰는 값은 `pending` / `sent` / `acked` / `no_ack` / `expired` / `rejected` 예요. 실패 쪽에 묶어 두셨다면 그대로 둬도 문제없어요.

## 6. 앱 §7·§8 회신 (2026-11-03)

### 6.1 §7 일일·주간 카드

1. **다음 날 시각 날짜 표기 — 요청대로 바꿨어요.** 날짜 없는 시각은 항상 `report_date` 그날의 시각이에요. 다른 날(다음 날 새벽 포함)의 시각에는 `M/D` 가 붙고, 범위 끝은 시작과 같은 날이면 날짜를 생략해요. 서버 PR #27(`4e5d527`)에 들어갔고, 아직 배포 전이라 처음 생기는 카드부터 이 형식이에요.

   | 이벤트(`report_date = 11/2`) | 카드 줄 |
   |---|---|
   | 11/2 14:00~15:00 | `14:00~15:00` |
   | 11/3 02:00~03:00 | `11/3 02:00~03:00` |
   | 11/2 23:30~11/3 00:40 | `23:30~11/3 00:40` |
   | 11/2 22:00~11/3 08:20 | `22:00~11/3 08:20` |
   | 11/1 23:10~11/2 09:30 | `11/1 23:10~09:30` |
   | 11/3 02:00~(진행 중) | `11/3 02:00~` |

   위 그래프(그날 자정~자정)와 날짜 없는 시각이 항상 같은 날이라 카드 위 "11/2 08:00 ~ 11/3 08:00 분석" 표기와 함께 헷갈리지 않아요. 주간 카드의 시간대 줄(`{H}시~{H+1}시 사이`)은 날짜를 쓰지 않아 바뀌지 않아요. [APP_DAILY_ANALYSIS_2026-11-02.md](APP_DAILY_ANALYSIS_2026-11-02.md) §시각도 고쳤어요.
2. **3단계(`ENV_REPORTS_ENABLED`)는 앱 배포 후** "켜도 됨"을 받고 켤게요. 2단계 푸시와 같은 배포에 묶는 것도 좋아요.
3. **카드 JSON**: 스위치를 켜고 실제 행이 생기면 서버가 운영 행 형식을 한 번 확인해서 알려 드릴게요. 모르는 `status` 는 칩 없이, 깨진 카드는 그 카드만 빼는 방어는 그대로 두세요.

## 7. 앱 §8(Stage O) 확정 회신 (2026-11-03)

§6.2 에서 "확정되면 알려 드릴게요"라고 한 항목을 확정했어요. 앱 0.168.0 가정이 **전부 맞습니다.** 상세 계약은 [APP_HUMID_CYCLE_2026-11-03.md](APP_HUMID_CYCLE_2026-11-03.md).

- `env_mist_gap` 이름 그대로, 두 kind 모두 `context.level = "caution"`(severity `warning`), message 는 `[환기 지연] 분무 후 건기 미도달` / `[건조 주의] 분무 필요`.
- **두 kind 모두 시작 푸시 1회**(1시간 추가 푸시 없음). 분무 공백도 푸시하므로 `env_humid` 수신 끄기 분기가 쓰입니다.
- 분무 공백은 최근 습기 이벤트가 **건기에 닿은 뒤** 15시간 동안 새 습기 이벤트가 없을 때만 나가요(아직 안 마른 사육장엔 안 나감). 환기 지연은 15시간이 지나도 안 마르면 조용히 닫힐 수 있어요(`closed_reason = "stale"`).
- 서버는 스위치 `HUMID_CYCLES_ENABLED` 꺼진 채 배포해요. 켜면 시각을 알려 드릴게요.
