## 1. 지금 생긴 증상 (왜 지금 공유하나)

운영 콘솔에서 사육장 2(terra-cb7cf18a) 보드의 공장 기본을 -1.5 → -2.0 으로 바꿨더니 **앱에 -0.5 가 표시**됩니다. 서버 DB 는 다음과 같습니다.

| 컬럼 | 값 | 뜻 |
|---|---|---|
| `devices.temp_offset_c` | -2.0 | 기기가 센서값에 더하는 절대값 (구 계약이 읽던 컬럼) |
| `devices.temp_offset_base_c` | -2.0 | 이 보드의 공장 기본 (신규, 11/10) |
| `devices.temp_offset_user_c` | **0.0** | 사용자 보정값 = 절대값 − 공장 기본. **앱이 보여줘야 하는 값** |

앱이 -0.5 를 보여주는 건 `temp_offset_c`(-2.0)에서 **앱 상수 -1.5 를 빼서** 표시하기 때문입니다(구 계약, `factoryDeviceValue`). 공장 기본이 -1.5 인 보드에서만 우연히 맞던 계산이라, 보드별 기본이 들어온 지금은 틀립니다. 신 계약(`temp_offset_user_c` 읽기)으로 가면 0.0 이 나옵니다.

## 3. 앱이 할 일

### 켜기 (0.174.6 스위치)
- **보내기**: `POST /devices/{id}/commands` `{ "action": "set_temp_offset", "payload": { "user_offset_c": <사용자값> } }`. 끔 = 0. `offset_c` 는 보내지 않음.
- **읽기·표시**: `devices.temp_offset_user_c` (PostgREST 조회 + `devices` Realtime UPDATE 의 `newRecord`). "저장 완료" 판정도 이 컬럼이 보낸 값(0.1 단위)과 같아지는 것으로.
- **상수 제거**: `factoryDeviceValue`(-1.5) 와 "`temp_offset_c` − 상수" 계산은 **반드시** 없앱니다. 공장 기본은 보드마다 다르고(-1.5, -2, -3 …) 운영 중 바뀔 수도 있어서 앱이 알 수 없고 알 필요도 없습니다. 서버가 `temp_offset_user_c` 로 계산해 줍니다.

### 범위 (Stage T 로 바뀐 점 하나)
- 11/05 에 안내한 사용자 범위 -8.5 ~ +11.5 는 공장 기본 -1.5 기준이었습니다. 이제 보드별로 달라집니다(기본 -3 보드는 -7 ~ +13). **앱은 범위를 하드코딩하지 말고** 서버 거절을 처리해 주세요.
  - 서버 응답: `POST` 즉시 400(`detail` 에 "user_offset_c 는 -7 ~ 13 범위" 같은 문구), 또는 큐잉 뒤 `commands.status=rejected`, `result=offset_out_of_range`.
  - UI 는 "이 보드에서 설정할 수 있는 범위를 벗어났어요" 정도면 충분합니다. 슬라이더를 쓰고 있다면 ±10 정도로 넉넉히 두고 거절만 처리해도 됩니다.
- `invalid_payload`(숫자 아님·키 두 개 동시) 는 앱 버그 방어용이라 정상 경로에선 안 나옵니다.

### 바뀌지 않는 것
- 엔드포인트·action 이름·Realtime 채널 그대로.
- `temp_offset_c` 컬럼은 계속 옵니다(절대값). 앱은 읽지 않으면 됩니다.
- `temp_offset_base_c` 는 앱이 읽을 필요 없습니다(운영 콘솔용).

### NULL 처리
- `temp_offset_user_c` 가 NULL 이면 **기기가 아직 보정값을 보고한 적 없음**(2026-10-01 이전 펌웨어, 또는 페어링 직후 첫 telemetry 전). 지금처럼 "미확인" 또는 0 표시. 구 펌웨어 보드는 `temp_offset_c` 도 NULL 이라 구 계약도 같은 처지였습니다.
