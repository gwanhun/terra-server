# 앱 전달 — 현재 온도가 "표시됐다 안 됐다" 하는 문제: 원인 분석과 표시 규칙

> **대상**: 앱 개발 담당
> **작성**: terra-server 백엔드 담당, 2026-09-28
> **성격**: 앱의 사육장 현재 온도가 간헐적으로 사라졌다 다시 나타나는 증상을 서버·DB·Realtime 경로까지 실측한 결과, **데이터는 빠짐없이 도착하고 있고 웹 콘솔(같은 경로)은 정상**이라 **앱의 표시 로직 문제**로 판단합니다. 서버 계약 변경은 없습니다. 아래 §3 표시 규칙에 맞춰 수정해 주세요.

## 1. 증상과 실측

**증상**: 기기 LCD에는 온도가 계속 표시되는데, 앱의 현재 온도는 나왔다 사라졌다를 반복. 웹 콘솔(`api.terra-server.uk`, 앱과 같은 Supabase Realtime 경로)에서는 같은 기기가 정상 표시됨.

> 참고: 9/28 이전 웹 콘솔은 마지막 행을 **나이 확인 없이** 계속 보여줬습니다(전원이 꺼진 기기도 온도가 살아 있는 것처럼 보임). 그래서 "웹은 정상"이 곧 "웹 로직이 맞다"는 뜻은 아니고, 데이터가 빠짐없이 온다는 근거는 아래 실측 2입니다. 웹 콘솔은 같은 날 §3 규칙대로 고쳐 앱의 참조 구현으로 쓸 수 있게 했습니다.

**실측 1 — DB 원본** (2026-09-28 03:09~07:09 UTC, 4시간)

| 항목 | 결과 |
|---|---|
| 연속 가동 기기 7대 | 각 4,700행 이상, **20초 넘는 공백 0건** |
| 서버(브리지·브로커) 원인 동시 공백 | **없음** (여러 기기가 같은 시각에 끊긴 구간 없음) |
| 센서 읽기 실패(`a_ok=false`) | 기기별 0~1.5%, 전부 **단발(3초 1샘플)** |

**실측 2 — Realtime 수신** (07:26 UTC부터 150초, 앱과 동일하게 `telemetry` INSERT 구독)

| 항목 | 결과 |
|---|---|
| 이벤트 누락 | **0건** (9대 모두 DB 행 수와 일치) |
| 도착 간격 | **3.3 ~ 4.1초** (기기 3초 주기 + 지연 흔들림) |
| 지연 (기기 `ts` → 수신) | 중앙값 0.9초, **최대 2.2초** |

즉 앱에는 3~4초마다 유효한 온도가 빠짐없이 들어옵니다. 그런데도 값이 사라진다면 **앱이 받은 값을 스스로 지우고 있거나, 받은 행을 파싱하다 예외로 버리고 있는 것**입니다(§2.5·§2.6).

**실측 3 — 오프라인 판정**: 기기 전원을 끈 뒤 `devices.is_online`이 false로 바뀌는 데 **221초 이상 ~ 318초 이하** 걸렸습니다(서버 규칙 180초 무응답 + 60초 주기 점검). 그 사이 `is_online`은 true이므로 앱이 "온라인인데 값이 없다"는 상태를 정상으로 다뤄야 합니다(§3.2).

## 2. 앱이 받는 데이터의 실제 성질

앱 표시 로직은 아래 여섯 가지를 전제로 설계해야 합니다.

### 2.1 도착 간격은 3초가 아니라 3~4초, 가끔 더 길다

기기는 3초 주기로 보내지만 WiFi·MQTT·DB INSERT·Realtime WAL 전달을 거치며 지연이 0.5~2초 흔들립니다. 따라서 **연속 두 값의 도착 간격은 3.3~4.1초가 정상**이고, 드물게 5~6초도 됩니다. "3초(또는 5초) 안에 새 값 없으면 `-`" 같은 규칙이 있으면 **매 주기 깜빡입니다.** 이 증상과 가장 잘 맞는 원인입니다.

### 2.2 센서 읽기 실패 행: `a_ok=false`, `t_a`/`h_a`는 NULL

DHT22 센서는 3초마다 한 번씩 비트뱅잉으로 읽는데 0.1~1% 확률로 타임아웃/체크섬 실패가 납니다. 이때 기기는 `ok:false`를 그대로 보고하고, 서버는 `t_a`/`h_a`를 **NULL로 저장**합니다(2026-09-15부터. 잘못된 값이 30분 집계를 오염시키는 것을 막기 위함). `a_ok`는 false로 남습니다.

- 실패는 거의 항상 **단발 1샘플**(3초)이고, 다음 행은 정상입니다.
- 기기 LCD는 이때 **마지막 정상값을 계속 표시**합니다(펌웨어가 의도적으로 그렇게 함). 앱도 같은 정책이어야 LCD와 앱이 일치합니다.
- 오늘(9/28) 펌웨어 드라이버의 타이밍 결함을 고쳐 실패율이 더 내려갈 예정이지만, **0이 되지는 않습니다**(배선·노이즈 요인). 앱은 NULL 행을 전제로 만들어야 합니다.

### 2.3 기기 재부팅·재접속 중엔 30초~수 분 동안 아무 행도 안 온다

전원 문제(브라운아웃), 전원 재투입, 와이파이 재접속 시 그 시간만큼 행이 없습니다. LCD는 로컬이라 계속 온도를 보여주지만 앱에는 새 값이 없습니다. 이 경우 앱은 **마지막 값 + "N초 전"** 으로 보여주고, 서버가 `devices.is_online=false`(180초 무응답)로 바꾸면 그때 오프라인 표시로 전환하는 것이 맞습니다. 재부팅 여부는 `devices.sys_state.uptime_s`/`reset`으로 알 수 있습니다.

### 2.4 보조 센서 B는 현재 항상 NULL

현재 출하 기기는 DHT22 B 센서가 제거돼 있어 `t_b`/`h_b`는 항상 NULL, `b_ok`는 항상 false입니다. 앱이 어딘가에서 B를 참조하면 그 자리는 항상 비어 보입니다. **메인 센서 A(`t_a`/`h_a`/`a_ok`)만 사용**하세요.

### 2.5 `t_a`/`h_a`는 정수로 올 때가 있다 (JSON 타입)

컬럼은 `FLOAT`이지만 Realtime·PostgREST는 소수부가 0인 값을 **소수점 없이** 직렬화합니다. 9/28 07:42 캡처 원문:

```json
{"t_a": 27,   "h_a": 43,   "a_ok": true, ...}   // terra-9e3f0f4a — 둘 다 정수
{"t_a": 30.3, "h_a": 72,   "a_ok": true, ...}   // terra-912ef88f — 습도만 정수
{"t_a": 28,   "h_a": 51.3, "a_ok": true, ...}   // terra-cf1e2da7 — 온도만 정수
```

Dart에서 `row['t_a'] as double`은 이때 `type 'int' is not a subtype of type 'double'`로 **예외**가 나고, 콜백이 중단되면 그 샘플은 화면에 반영되지 않습니다. 소수 첫째 자리가 0일 확률이 값마다 약 10%라 **온도·습도 중 하나가 정수인 샘플이 5개 중 1개꼴**이고, 이것만으로도 "표시됐다 안 됐다"가 납니다. 반드시 `(row['t_a'] as num?)?.toDouble()`로 받으세요. `led_brightness`는 항상 정수입니다.

### 2.6 신 펌웨어 기기는 `devices` 행 모양이 달라진다

9/28 펌웨어(원격 재부팅·진단 필드)를 올린 기기는 서버가 `devices` 행에 두 가지를 더 씁니다. `devices` UPDATE Realtime을 구독하거나 `/devices`·`from('devices')`로 모델을 만들 때 **엄격한 타입 파싱이면 여기서 예외**가 납니다. "펌웨어 업데이트 뒤로 더 안 보인다"면 가장 먼저 의심할 곳입니다.

| 필드 | 구 펌웨어 기기 | 신 펌웨어 기기 (9/28 캡처 원문) |
|---|---|---|
| `sys_state` | `null` | `{"heap": 2175856, "rssi": -29, "reset": "POWERON", "uptime_s": 1234}` — 3초마다 갱신 |
| `capabilities` | `{"board": "mosfet", "led_dimmable": true}` | `{"board": "mosfet", "mist_max_ms": 30000, "led_dimmable": true}` — **문자열·불리언·정수 혼합** |
| `firmware_ver` | `"terra-fw 4084a2a-dirty"` 등 | `"terra-fw a09772f-dirty"` |

- `capabilities`를 `Map<String, bool>`로 캐스트하거나 `led_dimmable`만 있다고 가정한 코드는 `mist_max_ms`(정수)에서 깨집니다. `Map<String, dynamic>`으로 받고 키별로 꺼내세요.
- `sys_state`는 없을 수도(구 펌웨어) 있을 수도 있습니다. 모르는 키는 무시하는 파서여야 합니다. 구조는 [APP_DEVICE_REBOOT_SYS_STATE_2026-09-28.md §3](APP_DEVICE_REBOOT_SYS_STATE_2026-09-28.md).
- `devices` UPDATE는 신 펌웨어에서도 여전히 **3초마다** 옵니다(`last_seen_at`·`sys_state`). 이 이벤트마다 화면 전체를 다시 만들거나 텔레메트리 상태를 초기화하면 매 주기 깜빡입니다. 바뀐 필드만 반영하세요.
- 리플래시 후 **해제 → 재페어링**하면 `devices` 행이 **새로 생깁니다**(같은 `hw_id`, 새 `device_id`·`id`). 옛 행은 `unlinked_at`이 찍히고 `enclosure_id`가 null이 되며, 더 이상 텔레메트리가 오지 않습니다(`is_online`은 true로 남을 수 있음). 앱은 `unlinked_at IS NULL`인 행만 목록에 쓰고, 사육장 화면은 `enclosure_id`로 현재 연결된 행을 찾아야 합니다.

## 3. 표시 규칙 (권장 구현)

기기별로 `{ lastGood: {t, h, ts}, lastRowTs, sensorFault: bool }` 상태를 두고, Realtime 행이 올 때마다 아래처럼 갱신합니다.

### 3.1 값은 덮어쓰기만 하고, 지우지 않는다

```dart
void onTelemetryRow(Map row) {
  final s = state[row['device_id']] ??= DeviceTelemetryState();
  s.lastRowTs = DateTime.parse(row['ts']);
  if (row['a_ok'] == true && row['t_a'] != null) {
    s.lastGood = (t: row['t_a'], h: row['h_a'], ts: s.lastRowTs);  // 정상 → 덮어씀
    s.sensorFault = false;
  } else {
    s.sensorFault = true;                                          // 실패 → lastGood 유지
  }
}
```

- `lastGood`은 **정상 행에서만** 갱신하고, 어떤 경로로도 `null`로 되돌리지 않습니다(화면 전환, 채널 재구독, 앱 복귀 포함).
- 부팅 시 초기값은 [APP_INTEGRATION.md §3.7](APP_INTEGRATION.md)의 "디바이스별 최신값" 조회로 채우되, `a_ok=true`인 최신 행을 골라야 합니다(`.eq('a_ok', true)` 추가).

### 3.2 신선도는 "지운다/안 지운다"가 아니라 3단계 표시

| 마지막 정상값 경과 | 표시 | 근거 |
|---|---|---|
| < 15초 | 값 그대로 (예: `27.4°C`) | 정상 도착 간격 3~4초, 지연 최대 2초의 여유 3배 |
| 15초 ~ 180초 | 값 유지 + 흐리게 + "N초 전" | 재접속·일시 지연. 값은 여전히 최근 것 |
| `devices.is_online == false` | 값 유지(더 흐리게) + "오프라인 · HH:MM 기준" | 서버 판정(180초 무응답). `devices` Realtime UPDATE로 받음 |

- 경과 시간 계산은 **앱 수신 시각 기준**이 아니라 `row.ts`(기기 SNTP 시각) 기준을 권장합니다. 다만 기기 시각이 미동기화면 서버 NOW()로 대체돼 있으니 어느 쪽이든 큰 차이는 없습니다.
- 15초 안쪽에서는 **어떤 UI 변화도 주지 않습니다.** 타이머로 값을 지우는 코드가 있다면 그것이 이번 증상의 직접 원인일 가능성이 가장 큽니다.

### 3.3 센서 실패 행은 배지로만

`sensorFault == true`이면 값은 `lastGood`을 그대로 보여주고 작은 경고 아이콘(예: "센서 확인 중")만 붙입니다. 다음 정상 행에서 자동으로 사라집니다. 실패가 **10회 이상 연속**(30초 이상)이면 그때 "센서 오류"로 승격해도 됩니다. 단발 실패에 값을 지우면 LCD와 앱이 어긋나 사용자가 혼란스러워합니다.

### 3.4 Realtime 채널은 하나를 오래 유지

- `telemetry` INSERT 채널은 로그인 후 1개 만들어 앱 수명 동안 유지합니다. 화면마다 만들고 끊으면 재구독 사이(수백 ms~수 초) 값이 비고, 끊는 코드가 상태를 초기화하면 값이 사라집니다.
- 상세 화면은 같은 채널의 콜백에서 `device_id`로 골라 쓰면 됩니다. 참조 구현: [web/index.html](../web/index.html)의 `telRemember`(정상 행만 `TEL_GOOD`에 저장), `telValueHtml`(3단계 신선도 + ⚠ 배지), `rt-devices` 채널 핸들러(`is_online` 반영). 채널은 1개, 값은 덮어쓰기만 하고 5초 타이머로 나이 표시만 갱신합니다.
- 앱이 백그라운드에서 돌아오면 채널이 끊겨 있을 수 있습니다. 재구독 후 §3.1의 최신값 1회 조회로 따라잡되, 그 동안 화면 값은 유지합니다.

### 3.5 그래프는 별도 규칙

시계열 그래프의 공백(선 끊기)은 [APP_TIMESERIES_CHART.md §4](APP_TIMESERIES_CHART.md)대로 **시간 간격**으로만 판단하고, `t_a` NULL 샘플은 건너뜁니다(NULL 하나에 선을 끊지 않음). 현재값 카드와 그래프의 규칙을 섞지 마세요.

## 4. 점검 체크리스트

앱 코드에서 아래를 찾아보면 원인이 바로 나올 가능성이 큽니다.

- [ ] 현재 온도를 `null`/`-`로 되돌리는 타이머·`Future.delayed`·`Timer.periodic`이 있는가? 임계값이 15초 미만인가?
- [ ] Realtime 콜백에서 `t_a == null`이면 상태를 `null`로 덮어쓰는가? (→ §3.3)
- [ ] `t_b`/`h_b`를 화면에 쓰는가? (→ §2.4)
- [ ] 화면 진입/이탈에서 채널을 `unsubscribe`/`removeChannel` 하고 상태를 초기화하는가? (→ §3.4)
- [ ] 콜백이 `device_id`를 비교하지 않고 마지막 행을 그대로 쓰는가? (여러 기기가 있으면 다른 기기 값이 번갈아 들어옴)
- [ ] `is_online` 판정을 앱이 자체 타이머로 하는가? (→ 서버 `devices.is_online`을 쓰고, `devices` UPDATE Realtime을 구독)
