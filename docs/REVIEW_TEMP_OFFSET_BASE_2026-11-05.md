## 1. 결정 항목

각 항목: 선택지 → 추천 → 근거 → 반대 의견/위험 → `결정:` 칸.

### D1. 공장 기본값(base)을 어디에 두나

| 선택지 | 내용 | 평가 |
|---|---|---|
| **A. 서버 env 상수** `TEMP_OFFSET_BASE_C` (기본 -1.5) | 전 기기 공통 1개 값 | ✅ 추천. 지금 활성 23대 전부 -1.5 기준(11/02 집계). 구현 최소 |
| B. 기기별 서버 전용 테이블 `device_calibration` (RLS 전면 차단) | 보드/센서별 값 | 나중에. 보드가 달라질 때 A 에서 B 로 옮기면 되고, 그때까지 빈 테이블만 생김 |
| C. `devices` 컬럼 (앱에서 컬럼 권한으로 숨김) | 기기별 값, 같은 테이블 | ❌ Realtime 은 컬럼 권한을 안 보고, PostgREST `select=*` 도 깨질 수 있어 "앱에 안 보임" 보장 불가 |

- 추천: **A**. 코드는 `base_c(device_uuid)` 시그니처로 열어 두고 지금은 env 만 읽는다(B 로 가는 길만 남김).
- 주의: **펌웨어 빌드 기본(`CONFIG_APP_TEMP_OFFSET_MDEG`)과 같은 값이어야 한다.** 다르면 flash erase 뒤 기기가 보고하는 -1.5 를 서버가 0 이 아닌 다른 사용자값으로 잘못 기록한다. 펌웨어 기본값을 바꾸면 서버 env 도 같이 바꾸는 규칙을 ENV.md 에 적는다.
- `결정:` ☐ A ☐ B ☐ C

### D2. `devices.temp_offset_c` 컬럼 — 의미를 바꾸나, 새 컬럼을 만드나

| 선택지 | 내용 | 평가 |
|---|---|---|
| **A. 기존 컬럼 의미 변경** (절대값 → 사용자값) | 스키마 변경 없음, COMMENT 만 수정 | ✅ 추천. 절대값은 어디에도 저장 안 함 → 앱이 볼 방법이 없음. 서버는 `사용자값 + base` 로 언제든 복원 |
| B. 새 컬럼 `temp_offset_user_c` 추가, 기존 컬럼 유지 | 둘 다 저장 | ❌ 기존 컬럼에 -1.5 가 남아 앱이 읽을 수 있다 → 요구사항 위반 |
| C. 새 컬럼 추가 + 기존 컬럼 삭제 | 깨끗하지만 | 콘솔·테스트·문서 전부 이름 바꿔야 함. A 와 결과 같고 일만 늘어남 |

- 추천: **A**. 배포 직후 다음 telemetry(3초 안)에 19대는 -1.5 → **0.0**, 콘솔로 -3.0 으로 조정한 1대는 → **-1.5** 로 바뀐다. 앱이 아직 이 컬럼을 안 쓰면(Q1) 영향 없음.
- `결정:` ☐ A ☐ B ☐ C

### D3. 합산(사용자값 → 기기값)을 어디서 하나

| 선택지 | 내용 | 평가 |
|---|---|---|
| **A. dispatcher 발행 직전** | 모든 경로(API·PostgREST 직접 INSERT·예약·콘솔)가 지나는 유일한 지점 | ✅ 추천. mist 분할과 같은 선례("DB 행은 요청값, 기기엔 변환값") |
| B. API(`POST /devices/{id}/commands`) | 저장 전에 합산해서 DB 에도 절대값 저장 | ❌ 앱이 `commands` 에 직접 INSERT 하는 경로(API.md §3.7)를 못 막는다. DB 에 절대값이 남아 앱 이력에 -1.5 가 보임 |
| C. DB 트리거 | INSERT 때 변환 | ❌ 앱이 자기 이력(payload)을 읽으면 절대값이 보임. 디버깅도 어려움 |

- `결정:` ☐ A ☐ B ☐ C

### D4. payload 키 이름 — `offset_c` 그대로 vs 새 키

| 선택지 | 내용 | 평가 |
|---|---|---|
| **A. `offset_c` 그대로, 의미만 "사용자값"으로** | 문서·콘솔·테스트 수정만 | ✅ 추천 — **Q1 답이 "앱 미배포"일 때만** |
| B. 새 키 `user_offset_c`, `offset_c` 는 과도기 절대값 통과 | 두 키 공존 | Q1 답이 "이미 배포"일 때 강제. 단 읽기 쪽(`devices.temp_offset_c`)은 양립 불가라 앱 강제 업데이트는 어차피 필요 |

- 추천: **A**. Q1 결과 따라 자동 결정.
- `결정:` ☐ A ☐ B (Q1 답: ______)

### D5. 합산 결과가 기기 허용 범위(±10℃) 밖일 때

| 선택지 | 내용 | 평가 |
|---|---|---|
| **A. 발행 전 거절** `status=rejected, result=offset_out_of_range` | unsupported_action 과 같은 패턴, 실패 푸시 경로 동일 | ✅ 추천. 앱이 즉시 결과를 본다 |
| B. ±10 으로 clamp 해서 발행 | 기기는 받음 | ❌ 사용자가 넣은 값과 적용값이 달라지는데 알릴 길이 없음 |
| C. 그대로 발행 → 기기 `bad_request` | 기기가 거절 | 동작은 하지만 왕복 1회 낭비, 메시지가 모호함 |

- 사용자값 허용 범위 = `-10 − base` ~ `10 − base` = **-8.5 ~ +11.5**. API 는 400 메시지에 이 범위를 **계산해서** 표기(상수 하드코딩 금지 — base 바꾸면 틀어짐). 앱 화면 범위(크기 0.1~4.0, 11/02 §1.2)는 넉넉히 안.
- `결정:` ☐ A ☐ B ☐ C

### D6. "보정 끔"에 앱이 보낼 값

- 11/02 계약: "끔 = **-1.5** 전송, **0 을 보내면 안 됨**(보드 발열이 그대로 실려 오경보)". 이번 구조에서는 **반대로 끔 = 0** 이 정답이고 -1.5 를 보내면 기기엔 -3.0 이 간다.
- 즉 11/02 §1.2 의 표를 **통째로 뒤집어** 전달해야 한다. 앱 계약 문서에 "폐기" 를 명시하고 새 표를 넣는다.
- 추천: 끔 = `offset_c: 0`. 서버가 `0` 과 "명령 없음"을 구분할 필요 없음(둘 다 기기 -1.5).
- `결정:` ☐ 확인

### D7. ACK(`CALIB` ok) 때 `devices.temp_offset_c` 를 서버가 확정하나

| 선택지 | 내용 | 평가 |
|---|---|---|
| **A. 안 함 (현행 유지)** | 기기 telemetry 보고만 진실 | ✅ 추천. 보드 교체·flash erase 뒤 어긋나는 문제를 피하려고 10/01 에 정한 원칙 |
| B. ACK ok 때 payload 값으로 확정 (lcd_text 방식) | 구 펌웨어 3대도 값이 생김 | 구 펌웨어는 어차피 보고를 안 해서 이후 어긋남을 못 잡음. 앱은 11/02 대로 ack 로 판정하면 됨 |

- `결정:` ☐ A ☐ B

### D8. 구 펌웨어(telemetry 에 `temp_offset_c` 없음, 3대)

- `devices.temp_offset_c = NULL` 유지. 앱은 "현재값 모름 → 보정 화면 막거나 업데이트 안내"(11/02 §1.2 그대로). 명령은 보낼 수 있고 합산도 정상 적용됨.
- 추천: **현행 유지**. 따로 할 것 없음.
- `결정:` ☐ 확인

### D9. 과거 `commands` 이력(절대값으로 저장된 `set_temp_offset` 행)

- 콘솔이 보냈던 이력(예: -3.0 1건, 그 외 -1.5 등)은 **절대값**이다. 바꾼 뒤 새 행은 사용자값이라 같은 컬럼에 두 의미가 섞인다.
- 선택지: A. 그대로 둠 + 콘솔 `🌡명령` 폴백 툴팁에 "2026-11-05 이전 이력은 절대값" 한 줄 / B. 과거 행 payload 를 일괄 UPDATE(+1.5) / C. 과거 행 삭제
- 추천: **A**. 앱은 이력을 보정 표시에 안 쓰고(ack 상태만 봄), 콘솔 폴백은 구 펌웨어 3대 전용이라 영향 작음. B·C 는 "사용자 데이터 임의 수정" 영역.
- `결정:` ☐ A ☐ B ☐ C

### D10. 관리자 콘솔(`web/beta.html`, `web/index.html`) 표기

- 바뀌는 것: 입력칸·현재값·온도 셀 모두 **사용자값** 기준. 관리자는 실제 기기값도 봐야 하므로 `/admin` 응답에 계산 필드 `temp_offset_device_c`(= 사용자값 + base) 를 추가해 `(기기 -0.5)` 로 괄호 표기.
- **반드시 서버와 같은 배포**: 지금 `beta.html` 은 `devices.temp_offset_c` 를 입력칸에 미리 채워 그대로 보낸다 → 서버만 먼저 배포하면 관리자가 [적용] 누르는 순간 0.0 이 들어가 멀쩡하지만, **배포 전 캐시된 페이지**에서 -1.5 가 미리 채워진 채 누르면 기기에 -3.0 이 간다. 배포 뒤 콘솔 새로고침 공지.
- `index.html` 온도 셀은 `/devices`(사용자 API) 를 쓰므로 사용자값만 보임 → 괄호 기기값은 `beta.html` 에만.
- 추천: 위 그대로.
- `결정:` ☐ 확인

### D11. 긴급 되돌리기(kill switch)

- `TEMP_OFFSET_BASE_C=0` 으로 두면 변환이 항등이 되어 **현행 동작과 같아진다**(코드 롤백 없이 env 만). 단 그 사이 저장된 사용자값과 의미가 섞이므로 "되돌리기" 는 앱이 아직 이 기능을 안 쓸 때만 안전.
- 추천: 코드 기본값은 -1.5, ENV.md 에 `0 = 변환 없음(비상용)` 명시. 별도 플래그는 만들지 않음(YAGNI).
- `결정:` ☐ 확인

### D12. 반올림·단위

- 사용자값·기기값 모두 소수 2자리 반올림(`round(x, 2)`), 콘솔·앱 표시는 1자리. 0.1 단위 입력에서 부동소수 오차(`-1.5 + 1.1 = -0.3999…`) 방지.
- `결정:` ☐ 확인

## 4. 배포 순서 (확정 뒤)

1. Q1 답 확인 → 이 문서 `결정` 칸 채우기 → 스펙 갱신

5. 앱 계약 문서 전달 → 앱 구현·배포
