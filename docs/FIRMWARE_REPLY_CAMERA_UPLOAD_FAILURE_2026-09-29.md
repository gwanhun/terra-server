## 1. 배경

- 테스트 A·B(신규FW)와 베타 카메라 전부에서 업로드 첫 시도 실패율이 60~78% 로 같고, WiFi 신호(−41~−53dBm) 와 무관했습니다.
- 실패는 모두 `stage=2, http=0`(R2 PUT 단계, 서버 거절 아님)이지만 **`err` 값이 두 종류**입니다. 정리본은 전부 "연결 실패" 로 묶었는데 DB 를 보면 다릅니다.

| 카메라 | last_err | 의미 |
|---|---|---|
| B (babdc226)·A (1e671d88, 9/30 12:15 시점) | stage 2, err **28674** (0x7002) | `ESP_ERR_HTTP_CONNECT`. R2 로의 TCP/TLS 연결이 15초(`HTTP_TIMEOUT_MS`) 안에 안 열림. DNS·TCP·TLS 중 어디서 막혔는지는 현재 코드로 구분 불가 |
| A (1e671d88, 9/29 16:24 시점)·테스트 외 카메라2 (1eda91af) | stage 2, err **-1** | `ESP_FAIL`. 연결은 됐고 그 뒤 실패: R2 write 15초 정체 / **SD 파일 읽기 중단**(`fread` 0) / 전송 바이트 불일치 셋 중 하나. **네트워크가 아닐 수 있음** |

  A 의 78% 유실을 R2 연결 문제로만 보면 SD 카드 문제를 놓칩니다. 둘을 가르는 세부 코드가 §5 항목 2 입니다.
- 인증서 문제도 아닙니다. R2 가 내주는 체인(leaf → WE1 → GTS Root R4)은 펌웨어가 `r2_ca.h` 에 고정한 것과 6회 조회 모두 일치했습니다.

## 2. 유력 원인 — R2 엔드포인트 IP 하나가 가정 회선에서 불통 (서버 정상 · 테스터 집 확인 요청)

R2 업로드 주소(`R2_ENDPOINT` 의 호스트, `<account>.r2.cloudflarestorage.com`)는 IP 두 개로 풀립니다. 9/29 밤 펌웨어 담당 자택(KT 회선)에서 측정:

| IP | ping | TCP 443 | TLS 핸드셰이크 |
|---|---|---|---|
| 172.64.190.1 | 정상 (avg 9.7ms) | 열림 | 0.02초 |
| 172.64.66.1 | **100% 손실** | **연결 실패** | 12초 타임아웃 (4/4회) |

traceroute 는 KT 백본(116.43.128.45) 다음 홉부터 응답이 없습니다.

**펌웨어가 이걸 못 피하는 이유**

- `CONFIG_LWIP_DNS_MAX_HOST_IP=1`: DNS 응답에서 IP 를 **하나만** 보관합니다. 그게 172.64.66.1 이면 그 클립은 15초 뒤 `ESP_ERR_HTTP_CONNECT` 로 끝나고, 다른 IP 로 넘어가는 폴백이 없습니다.
- lwIP 는 DNS 결과를 TTL 동안 캐시하므로 실패가 몇 분 단위로 뭉칩니다. (같은 시간대 클립이 연달아 실패하는 패턴이 있으면 이것과 일치)
- 데스크톱/폰은 첫 IP 가 실패하면 자동으로 둘째 IP 를 시도해서 6초쯤 걸리고 성공합니다. 그래서 사람 눈에는 R2 가 멀쩡해 보입니다.

**확인 결과 (9/30 새벽, Lightsail 서버 = AWS 서울)**: 두 IP 모두 정상 (`http=400`, connect 0.017s / 0.003s. 400 은 빈 요청을 R2 가 거절한 것으로 연결 자체는 성공). 즉 **Cloudflare 전역 장애는 아니고, 가정용 회선 경로 문제로 좁혀집니다.** 카메라는 전부 가정집에 있으므로 서버 결과보다 집 회선 결과가 카메라 상황에 가깝습니다. 실패율이 50% 가 아니라 60~78% 인 것은 DNS 응답 순서와 lwIP 캐시(TTL 동안 같은 IP 고정) 때문에 나쁜 IP 에 걸리면 몇 분간 연달아 실패하기 때문입니다.

| 측정 위치 | 172.64.190.1 | 172.64.66.1 |
|---|---|---|
| Lightsail (AWS 서울) | 정상 | **정상** |
| 펌웨어 담당 자택 (KT) | 정상 | **불통** (ping 100% 손실, TCP 443 실패, KT 백본 다음 홉부터 무응답) |
| 테스터 집 (A·B·C 설치 집) | 미확인 | **미확인 — 확인 요청** |

**확인 부탁드립니다.** 테스트 카메라가 있는 집에서 노트북으로 한 번 (맥은 그대로, 윈도우는 Git Bash):

```bash
H=1ab01a2c48f3e8015e7b880562188917.r2.cloudflarestorage.com
for ip in 172.64.66.1 172.64.190.1; do
  curl -s -o /dev/null -m 10 --resolve "$H:443:$ip" \
       -w "$ip http=%{http_code} connect=%{time_connect}s\n" "https://$H/" || echo "$ip FAIL"
done
```

- 172.64.66.1 이 `http=000` + FAIL → 카메라 B 계열(err 28674) 실패 원인 확정. KT 한정인지 여러 ISP 인지는 테스터 집 회선 종류로 판단.
- 둘 다 정상 → 그 집의 카메라 실패는 다른 원인. §5 항목 2 의 세부 코드가 들어가야 갈립니다.

어느 쪽이든 펌웨어가 IP 하나에 매달리는 구조가 문제라는 점은 같아서 §5 항목 1(DNS 폴백)은 그대로 진행합니다. 세부 코드(항목 2)가 들어가면 카메라가 어느 IP 에서 실패하는지 집집마다 자동으로 보고되어 이런 수동 확인이 필요 없어집니다.

## 3. 업로드 동작 질문 4건 답변

코드 기준: `main/uploader.c` `terra_uploader_upload_clip()` 이 **upload-url POST → R2 PUT(mp4) → R2 PUT(썸네일, 실패해도 진행) → 메타 POST** 를 한 번에 수행하고, 재시도는 이 함수를 **처음부터 다시** 부르는 방식뿐입니다.

### ① 재시도 때 upload-url 을 새로 받나, 처음 URL(5분)을 재사용하나

- **신규FW(0.2.0)**: 재시도 자체가 없습니다. 실패 클립은 즉시 폐기(`APP_CLIP_UPLOAD_RETRY=n`).
- **구FW(0.1.0, SD 재시도 있는 빌드)**: `sd_retry_task` 가 같은 함수를 다시 부르므로 **매번 새 upload-url 을 받고, clip_id 도 새로 발급**됩니다. 처음 URL 재사용은 없습니다. 따라서 URL 만료(5분)는 실패 원인이 아닙니다.

### ② 영상 업로드 후 메타 등록 응답을 못 받으면 메타를 다시 보내나

- 즉시 재전송은 없습니다. `fail_stage=3` 으로 기록하고 종료합니다.
- 신규FW 는 폐기. 구FW 는 다음 주기에 **새 clip_id 로 처음부터** 다시 → mp4 를 한 번 더 PUT 하고 이전 mp4 는 R2 에 고아로 남습니다(`scripts/reconcile_r2_orphans.py` 대상).
- 결론: **같은 clip_id 로 메타를 두 번 보내는 경우는 펌웨어에서 발생하지 않습니다.** PR #7 의 중복 메타 200 처리는 무해하지만 펌웨어가 쓰는 경로는 아닙니다.

### ③ 메타 등록 성공 판정은 201 만인가, 2xx 전체인가

- **2xx 전체**입니다. upload-url·R2 PUT·메타 세 단계 모두 `status < 200 || status >= 300` 이면 실패 (`uploader.c` L481·L510·L557). 8월 베이스라인 빌드(구FW)도 동일합니다.
- 따라서 PR #7 에서 재전송에 200 을 돌려줘도 펌웨어는 성공으로 봅니다.

### ④ 재시도 간격·백오프

| | 신규FW 0.2.0 | 구FW 0.1.0 (SD 재시도 빌드) |
|---|---|---|
| 즉시 업로드 | 녹화 직후 1회 | 녹화 직후 1회 |
| 실패 시 | 폐기, 재시도 없음 | SD 에 보관 후 `sd_retry_task` 가 재업로드 |
| 재시도 주기 | — | **60초 고정** (`APP_SD_RETRY_PERIOD_S=60`), 백오프 없음 |
| 주기당 | — | 가장 오래된 백업 **1건** |
| 횟수 제한 | — | 없음 (성공할 때까지) |
| 우선순위 | — | 즉시 업로드가 TLS 락(`s_upload_lock`)을 먼저 잡으면 그 주기는 건너뜀 |

err 28674 = `ESP_ERR_HTTP_CONNECT` (0x7000+2) 로 보신 것 맞습니다.

## 4. 분석 메시지에 대한 정정 2건 + 요청 ③ 답

### 4.1 "SD 저장 자체가 대부분 실패" 는 카운터 오독입니다

`clip_stats.sd_ok / sd_fail` 은 SD **쓰기** 결과가 아니라 **SD 백업 재업로드** 결과입니다 (`main.c` L2966 주석 "SD 재업로드 결과"). 카메라10 의 `sd 150/430` 은 "재업로드 150번 성공, 430번 실패" 이고, 실패 원인은 §2 와 같은 connect 실패입니다. 즉 "업로드 실패 → SD 저장도 실패" 의 이중 실패가 아니라 **같은 연결 실패가 60초마다 반복 카운트**된 것입니다. SD 쓰기 실패는 별도 로그(`clip SD 쓰기 오류`)로만 남고 카운터가 없습니다.

### 4.2 문범석 4738 (p4cam-ac5cd849) 은 다른 유형이 맞습니다

9/29 16:25 하트비트: uptime 99h, rec 34, 마지막 녹화 = 부팅 48분 뒤, 이후 `skip=0, skip_lock=0, up_busy_s=-1`. 슬롯 부족·락 실패·업로드 정체 카운터가 전부 0 이므로 구FW 의 "업로드 무한루프가 슬롯을 쥠" 유형이 **아닙니다**. 프레임 공급이나 모션 감지가 조용히 선 유형이라 크래시/워치독에 안 걸립니다. 재부팅 전에 카메라 LAN 에서 `/status`(Basic 인증) 를 받아 `recording.active`, `webrtc.last_video_age_ms`, `memory.psram_largest_kb` 를 보는 것이 유일한 단서입니다.

### 4.3 (요청 ③) A 의 `sd_backlog` 가 계속 늘어나는 원인 — 펌웨어 버그

`sd_backlog` 는 SD 폴더의 `.mp4` 파일 수를 60초마다 센 값입니다. 신규FW 는 업로드 성공·실패와 무관하게 `clip_sd_delete()` 로 지우므로 원칙상 0 근처여야 하는데, 파일이 남는 경로가 둘 있습니다.

| # | 경로 | A 해당 여부 |
|:---:|---|---|
| 1 | **삭제 실패를 무시.** `clip_sd_delete()` 가 `unlink()` 반환값을 버림 (`clip_sd.c` L373). SD 카드가 불안정해 FAT 갱신이 실패하면 파일이 남고 로그·카운터가 없음 | **유력.** A 가 err -1(§1, SD 읽기 실패 가능) 도 기록한 것과 맞물림. A 의 `/status` 에서 `sd.write_errors` 가 0 이 아니면 확정 |
| 2 | **업로드 큐가 차면 클립을 버리면서 SD 파일은 안 지움.** `main.c` L3554 "queue full — dropping clip" 경로가 메모리만 해제 | **아님.** 이 경로는 `rec` 만 늘고 `up_ok/up_fail` 은 안 늘어 구분되는데, A 는 `rec 123 = up_ok 38 + up_fail 85` 로 한 번도 안 탔음 |

둘 다 다음 빌드에서 고칩니다(§5 항목 4). 구FW 카메라의 `sd_backlog` 는 이것과 무관하게 재업로드 대기 파일 수가 맞습니다.

## 5. 펌웨어 후속 계획

| # | 항목 | 내용 | 시점 |
|:---:|---|---|---|
| 1 | **DNS 폴백** | `CONFIG_LWIP_DNS_MAX_HOST_IP` 2 이상 + R2 PUT connect 실패 시 다른 IP 로 즉시 1회 재시도 (esp_http_client `common_name` 으로 SNI·인증서 검증 유지) | 코드는 즉시. 플래시는 A/B 테스트 1차 판정(10/1 00시) 뒤 A·B 부터 → 실패율이 78% 에서 한 자릿수로 떨어지면 원인 확정 |
| 2 | **실패 세부 코드** (정리본 요청 ①) | `last_err.detail` 추가: `dns / tcp / tls / write_stall / sd_read / len_mismatch / http`. DNS 는 PUT 전 `getaddrinfo` 시간·받은 IP 기록, TCP vs TLS 는 `HTTP_EVENT_ERROR` 에서 `esp_tls_get_and_clear_last_error()` 로 구분, SD 읽기는 `fread` 0 일 때 `ferror()` 로 판정. 실패 시점 internal/PSRAM largest block 과 라이브 동시 여부도 함께 | 1 과 같은 빌드 |
| 3 | **조용한 정지 워치독** (정리본 요청 ②) | "N시간 녹화 0건" 단독은 야간 미활동과 구분이 안 되어 오탐. **녹화 0건 AND 라이브 offer 에 프레임이 안 나옴(`last_video_age_ms`)** 조합으로 재부팅. **기존FW 에는 넣을 수 없음** — P4 는 OTA 가 없어 어떤 변경이든 리플래시 = 신규FW | 1 과 같은 빌드 |
| 4 | **sd_backlog 버그 수정** (정리본 요청 ③) | `clip_sd_delete()` 실패 로그·카운터 추가, 큐 풀 드롭 시 SD 파일도 삭제 (§4.3) | 1 과 같은 빌드 |
| 5 | 실패 클립 즉시 폐기 정책 | 폴백 후 실패율을 보고 결정. 여전히 높으면 "재시도 3회 상한 + 백오프" 로 전환 | 1 결과 확인 뒤 |

P4 는 OTA 가 없어 매 변경이 물리 리플래시입니다. 그래서 1~4 를 한 빌드로 묶습니다. 플래시 시점은 A/B 테스트 1차 판정(10/1 00시) 뒤 A·B 부터가 제안이며, 확정은 owner 결정 대기.
