## 1. 결론 (한 줄)

- 서버·브로커·OTA 인프라 문제 아님. 같은 공유기에서 나노가 같은 브로커(8883/TLS)에 계속 붙어 있음.

## 5. 펌웨어 측 분석과 조치

### 5-1. `no_time` 이 등록을 막던 구조 (0.4.5.1 까지) — **수정 완료**

- BLE 등록 워커가 SNTP 동기화 15초를 **필수 조건**으로 걸었음. 그런데 lwIP 기본값(시작 지연 0~5초, 응답 대기 15초, 재시도 간격 15→30→…→150초)이라 15초 창에 사실상 **한 발**만 나감. UDP 한 개 유실 = 등록 실패. 한 번 실패하면 재시도 간격이 늘어 연달아 눌러도 계속 실패.
- `CONFIG_LWIP_SNTP_MAX_SERVERS=1` 이라 코드의 두 번째 서버(`time.google.com`)는 lwIP 가 조용히 무시 → 백업 서버가 애초에 없었음.
- 결정적으로 `CONFIG_MBEDTLS_HAVE_TIME_DATE` 가 꺼져 있어 **TLS 는 시각 없이도 동작**. 실제로 부팅 경로(`cloud_task`)는 SNTP 결과를 무시하고 MQTTS 로 진행해 왔음. 등록만 막았던 것이 모순.
- 0.4.8 (카메라) / 0.3.4 (허브):
  - SNTP 서버 3개 실제 등록(`pool.ntp.org`, `time.google.com`, `216.239.35.0` IP 리터럴), 시작 지연 제거, 6초마다 `esp_sntp_restart()` 로 백오프 끊고 다른 서버에 재발사, WiFi 연결 직후 선시작.
  - **등록은 소프트 게이트**: 10초 기다려 보고 못 맞춰도 HTTPS 등록 진행. `no_time` 은 **시각도 못 맞추고 HTTPS 도 실패**했을 때만 보고 → 뜻이 "이 WiFi 에서 서버로 아무것도 안 나감".
  - SNTP 실패를 `sntp: Ns 동기화 실패 (dns a/b)` 로 `camera_logs` 에 전송(단, MQTT 가 붙은 뒤에야 도착).
- 실기: `p4cam-e9570387` 0.4.8 OTA verified, 콜드부트 후 20초 재접속 확인.

### 5-2. 0.4.8 에서도 `no_time` 이 나는 이유

- 이제 `no_time` = 그 10~25초 동안 NTP(UDP 123)도, `POST /cameras/pair`(TCP 443)도 서버에 못 닿음. 같은 공유기에서 몇 분 뒤 MQTT(TCP 8883, 같은 서버 IP)는 붙음 → 포트 차단·서버 문제가 아니라 **그 순간 이 카메라의 무선 링크가 바깥으로 안 나가는 상태**.
- 등록은 "그 순간" 한 번만 시도하므로 링크가 들쭉날쭉하면 운에 좌우됨. 나노는 같은 공유기에서 멀쩡하므로 공유기 회선은 정상.

### 5-3. 새로 발견된 펌웨어 이슈 (별건, 미수정)

- **esp-hosted 패닉**: `assert failed: hosted_memcpy port_esp_hosted_host_os.c:74 (src)`, 태스크 `ble_prov_cmd`, 직전 `hosted_memcpy:71 dest is NULL`. BLE 재설정을 짧은 간격으로 반복하는 중 1회. 함대 전체에서 첫 관측. 재부팅으로 복구.
- **WebRTC 루프 스톨 워치독**: 네트워크가 죽어 있으면 `esp_peer_main_loop` 가 30초 블록 → 57초마다 재부팅 루프. MQTT 미연결 상태에서는 WebRTC 를 띄우지 않거나 재부팅 대신 세션만 닫는 것이 맞음.
- **OTA 명령 유실**: MQTT clean session 이라 끊긴 사이 발행된 `ota_prepare` 는 버려짐. 접속이 들쭉날쭉한 기기용으로 "pending 작업이 있는 기기에서 하트비트가 오면 재발행" 을 서버에 넣으면 명령 유실은 막힘(다운로드는 별개).

## 5-4. 왜 핫스팟에서는 등록되고 공유기에서는 안 되나

"연결" 을 세 단계로 나눠야 설명이 된다. 단계마다 쓰는 프로토콜이 다르고, 두 네트워크는 막히는 단계가 다르다.

| 단계 | 프로토콜 | 공유기 `38:f4:5e` | 핫스팟 `92:66:c1` / `6e:11:31` |
|---|---|---|---|
| ① 시각 동기화 | UDP 123 (NTP) | **거의 항상 실패** (콜드부트마다 `no_time`) | 한두 발 안에 성공 |
| ② 등록 `POST /cameras/pair` | TCP 443 (HTTPS) | 간헐 실패(`ESP_ERR_HTTP_CONNECT`), 특히 WiFi 를 런타임에 바꾼 직후 | 첫 시도 실패 후 재시도 성공 (2회 모두) |
| ③ 운영 MQTT | TCP 8883 (MQTTS) | 깨끗한 부팅 뒤 23~32초 안에 접속. 이후 간헐 타임아웃 | 15~20초마다 끊김, PING_RESP 유실, 워치독 재부팅. OTA 다운로드 실패 |

- **0.4.5.1 까지**: ①이 등록의 필수 조건이었다. 공유기에서는 ①이 안 되니 ②를 시도조차 안 하고 `no_time`. 핫스팟에서는 ①이 되니 ②로 넘어가 등록 성공. 이게 "핫스팟은 되고 공유기는 안 되는" 현상의 **직접 원인**. 그런데 ③은 ①과 무관하므로(TLS 가 시각을 안 봄) 공유기에서도 이미 등록된 카메라는 돌아간다 — 그래서 아침에 공유기에서 하트비트가 들어왔다.
- **0.4.8 부터**: ①은 선택이 됐고 ②만 통과하면 된다. 공유기에서 ②가 실패하는 경우가 남아 있는데, 로그상 세 번 모두 **BLE 로 WiFi 를 런타임에 갈아탄 직후**(`wifi link drop: reason=8` 뒤 30~40초)에 났다. 같은 공유기에서도 재부팅 후 깨끗하게 붙은 부팅에서는 MQTT 가 23초 만에 연결됐다. 즉 "공유기에서 아예 안 나가는" 게 아니라 **갈아탄 직후 창에서 새 TCP 연결이 안 열리는** 쪽이 더 정확하다. 펌웨어 주석(`ble_provisioned_cb`)도 런타임 전환 뒤 네트워크 스택이 옛 네트워크에 묶인다는 이유로 재부팅을 택하고 있는데, 등록(②)은 그 재부팅 **전**에 실행된다.
- 공유기가 NTP 를 막는 이유는 공유기 설정(보안/방화벽에서 UDP 123 차단, 또는 ISP 의 NTP 리다이렉트 미동작)으로 추정. 확인은 그 WiFi 에 붙은 폰에서 NTP 앱이나 `ntpdate` 류로 1분 안에 가능.

## 5-5. 나노(긱블 보드)는 되는데 카메라 보드는 안 되는 이유

같은 자리, 같은 공유기, 같은 서버인데 결과가 갈린 건 **보드도 다르고 등록 로직도 다르기 때문**이다. 둘 다 작용했다.

| 항목 | 나노 (terra-iot, ESP32-S3) | 카메라 (P4 + ESP32-C6, esp-hosted SDIO) |
|---|---|---|
| WiFi 하드웨어 | S3 내장 WiFi, 드라이버가 같은 칩 안 | P4 에는 WiFi 가 없음. C6 모듈에 SDIO 로 원격 WiFi(`esp_wifi_remote`). 라디오·안테나·드라이버 경로가 전혀 다름 |
| 시각 동기화 | `esp_netif_sntp` 10초 대기 후 **무조건 진행** | 0.4.5.1: 15초 안에 못 맞추면 **등록 거부**(`no_time`). 0.4.8: 10초 소프트 대기 후 진행 |
| 등록 시도 방식 | `cloud_pair_task` 가 **무한 루프**로 재시도. HTTPS 가 실패하면 `PAIR_FAIL` 알리고 다음 바퀴에 다시 시도. BLE 명령 1회에 묶이지 않음 | BLE `CONNECT` 1회당 HTTPS **1회**. 실패하면 끝. 사용자가 다시 눌러야 하고, 그 사이 재부팅이 끼면 WiFi 도 다시 붙여야 함 |
| WiFi 변경 뒤 처리 | 재부팅 없이 그대로 진행 | 등록 뒤 재부팅(런타임 전환 후 스택이 옛 네트워크에 묶이는 문제 회피). 그런데 등록 자체는 재부팅 **전**, 가장 불안정한 창에서 1회 실행 |
| 동시 TLS 세션 | MQTT 1개 | MQTT + HTTPS 업로드 + WebRTC/TURN. 링크가 흔들리면 체감이 훨씬 큼(워치독 재부팅까지) |
| 오늘 현장 결과 | 11:04 등록 후 끊김 없이 온라인 | 같은 공유기에서 NTP 실패·HTTPS 간헐 실패·MQTT 타임아웃 |

정리하면:
1. **공유기에서 NTP 가 막혀 있다** → 나노는 신경 안 쓰고 넘어가고, 옛 카메라는 여기서 멈춘다. (0.4.8 에서 해소)
2. **HTTPS 가 간헐적으로 실패한다** → 나노는 자동 재시도로 결국 통과하고, 카메라는 한 발 실패가 곧 `timeout`/`no_time` 이다. (0.4.8 에도 남아 있음 → 후속 1번)
3. **무선 자체가 이 자리에서 C6 만 불안정하다** → 나노의 S3 는 멀쩡한데 카메라의 C6 는 공유기·핫스팟 모두에서 패킷을 흘린다. 이 카메라가 다른 장소에서 3주간 무결점이었으니 보드 고장보다는 **이 현장 2.4GHz 와 C6 의 궁합**(채널 혼잡·과포화·AP 설정)이 유력. 원격으로는 여기까지. 확정은 §6 의 A/B.

### 후속 개선 후보 (펌웨어)
1. **[0.4.9 / 허브 0.3.5 에 포함]** BLE 등록에서 HTTPS 가 서버 미도달(`timeout`)로 실패하면 3초 간격 **최대 3회 재시도**(BLE 대기 70초). 401/4xx/5xx 는 즉시 종료. 핫스팟에서 "첫 실패 → 재시도 성공" 패턴이 두 번이라 효과가 확실하다. 같은 빌드에 C6 WiFi 초기화 재시도(부팅 시 esp_wifi_init 4회, 실패 시 사유 남기고 재부팅)도 들어 있다 — 부팅 경로 변경이라 OTA 는 1대 선검증 후 전개.
2. 또는 `s_cloud_started` 상태에서 CONNECT 가 오면 **먼저 재부팅하고 새 네트워크에서 깨끗하게 등록**하도록 순서 변경(앱 프로토콜 영향 있음 — PAIR 결과를 재부팅 뒤에 알려야 함).
3. NTP 가 막힌 환경 대비 **HTTP `Date` 헤더로 시각 보정**(평문 HTTP 리다이렉트 응답의 Date 만 읽음). 클립 타임스탬프·업로드 창이 필요로 함.

## 6. 남은 문제와 현장에서 가를 방법

원격 데이터로는 "이 보드 + 이 현장 2.4GHz" 까지만 좁혀짐. 아래 중 하나로 확정 가능:

1. **다른 P4 카메라를 같은 자리, 같은 공유기에** 붙여 본다. 똑같이 끊기면 현장(공유기 설정/간섭), 멀쩡하면 이 보드(C6 안테나·조립).
2. **이 카메라를 사무실 AP(`b0:38:6c…`)로 가져와** 본다. 3주간 그랬듯 멀쩡하면 보드 불량은 아님.
3. 현장에서 시리얼(`idf.py monitor`) 로 부팅 로그 캡처: `wifi ps[got_ip]: readback=`(NONE 이어야 함), `dns servers:`, `got ipv6`, `SNTP …`, `esp-tls` 에러. 이 로그는 서버로 안 올라옴.

공유기 쪽에서 바로 해볼 수 있는 것(비용 0):
- 카메라를 공유기에서 2~3m 이상 떨어뜨린다(-35dBm 은 과포화 구간).
- 2.4GHz 채널 1/6/11 중 하나로 고정, 대역폭 20MHz, 보안 WPA2-PSK 전용(WPA3/PMF 끔), 2.4GHz 의 802.11ax 끔, 밴드 스티어링(스마트 커넥트) 끔.
- 폰 핫스팟은 끈다(같은 채널 간섭 + 카메라가 핫스팟으로 되돌아감 방지).
- 바꾼 뒤 카메라 전원만 한 번 뺐다 꽂는다.

## 7. 운영/앱 안내

- 등록이 `no_time` 또는 `timeout` 으로 실패하면 **unlink 하지 말고** 같은 자리에서 1~2분 뒤 재시도. unlink 는 MQTT 자격증명을 해지해 그 사이 "오프라인"을 만들고, 매번 새 camera_id 가 생겨 이력이 끊긴다.
- 등록이 한 번 성공한 카메라는 전원을 뺐다 꽂아도 그 공유기에서 다시 붙는다(0.4.8). 등록만 HTTPS 1회 성공이 필요.
- 앱 문구 제안: `no_time` → "이 WiFi 에서 인터넷 연결을 확인하지 못했어요. 공유기 가까이가 아니라 1~2m 떨어진 곳에서 다시 시도하거나 다른 WiFi 를 선택하세요." (`timeout` 과 동일 안내로 묶어도 됨.)
