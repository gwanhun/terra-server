## 3. 3번 — `cameras` 트리거 3개 검토

### 3.1 우리 트리거와 겹치지 않습니다

| | 시점 | 컬럼 | 하는 일 |
|---|---|---|---|
| **petcam** | BEFORE INSERT | — | labeling_group·이름 접미사 승계 |
| **petcam** | AFTER INSERT | — | 라벨러 배정 복사, `motion_clips` 이관 |
| **petcam** | BEFORE UPDATE OF `name` | name | 접미사 재부착 |
| terra-server | AFTER UPDATE OF `enclosure_id` | enclosure_id | `redesign_touch_assignments` → 배정 이력 reconcile (`2026-09-16_app_redesign_03`) |

INSERT 에는 우리 트리거가 없고, UPDATE 는 서로 다른 컬럼입니다. 같은 문장에서 둘 다 타는 경우가 없습니다. fail-open 설계도 확인했습니다 — 등록 자체를 막지 않는 게 맞습니다.

### 3.2 언제 타고 언제 안 타나

| 등록 경로 | 서버 동작 | petcam INSERT 트리거 |
|---|---|---|
| 베타 콘솔 `[카메라]` 등록 | **항상 INSERT** (콘솔이 hw_id 를 모름 — §4) | ✅ 탐 |
| 삭제/해제 후 재등록 | **INSERT** (의도적 — §4) | ✅ 탐 |
| 펌웨어 자체 재페어링 (BLE, 해제 안 함, hw_id 일치) | **UPDATE** (기존 행 재사용, 9/21~) | ❌ 안 탐 — **정상**. 같은 행이라 이관할 게 없음 |

즉 트리거가 안 타는 유일한 경우는 "이관할 필요가 없는" 경우입니다. 지금 보고 계신 8636 같은 케이스(삭제→재등록)는 정확히 INSERT 라 트리거가 맞는 표적입니다. **걷지 마세요.**

### 3.3 질문 — `BEFORE UPDATE OF name` 의 범위

"이름에 `·` 가 없고 직전 카메라에 접미사가 있으면 다시 붙임" — 사용자가 **앱에서 의도적으로** 이름을 바꾼 경우(예: `카메라 8 · 8636` → `거실 게코`)에도 `거실 게코 · 8636` 이 되는 걸로 이해했습니다. 라벨링 식별용이면 그게 의도겠지만, 테스터 눈에는 "내가 지운 꼬리가 다시 붙는다"로 보일 수 있어 확인차 여쭙습니다.

### 3.4 제안 — 접미사 대신 `hw_id` 로 매칭

9/21 부터 `cameras.hw_id` (보드 efuse MAC, 12자리 hex) 가 있습니다. 펌웨어가 **페어링과 telemetry 양쪽**에서 보내므로, 구 펌웨어로 등록된 행도 새 펌웨어로 올라오면 채워집니다. "직전 카메라" 판정을 이름 끝 4자리 대신 `(owner_id, hw_id)` 로 하면 이름을 바꿔도 안 깨집니다. `merge_reregistered_camera_clips.py` 에도 같은 키를 쓸 수 있습니다. 단 hw_id 가 NULL 인 행(구 펌웨어·미부팅)은 여전히 접미사 폴백이 필요합니다.

## 4. 문의 ① — 멱등 페어링: 부분 예

**요청하신 것은 9/21 에 이미 들어갔습니다** (`5927dfd`, `2026-09-21_cameras_hw_id.sql`). `/cameras/pair` 는 같은 owner 에 같은 `hw_id` 인 **활성 행**이 있으면 INSERT 대신 그 행을 UPDATE 하고 토큰만 재발급합니다. 펌웨어는 efuse MAC 을 hw_id 로 보냅니다.

그런데 새 행이 생기는 경로가 **둘** 남아 있고, 하나는 구조적, 하나는 의도적입니다:

| 경로 | 새 행? | 이유 |
|---|:---:|---|
| 펌웨어 자체 페어링 (BLE 프로비저닝) | ❌ | hw_id 일치 → 재사용 ✅ |
| **베타 콘솔 등록** | ⭕ | 콘솔은 운영자가 발급만 하고 카메라는 그 토큰으로 MQTT 에 붙을 뿐 — **`/cameras/pair` 를 카메라가 호출하지 않으므로 hw_id 를 보낼 주체가 없음** |
| **삭제/해제 후 재등록** | ⭕ | 조회가 `unlinked_at IS NULL` 로 제한됨. **사용자가 의도적으로 해제한 카메라를 페어링이 몰래 되살리면 안 되기 때문** — 이건 고치지 않을 설계입니다 |

8636 의 8행은 이 둘의 조합입니다. 그래서 **"새 행에 이전 설정을 승계"** 하는 petcam 트리거 방향이 맞고, 서버가 대신할 수 있는 건 베타 콘솔 경로를 줄이는 것뿐입니다(운영자가 보드 MAC 을 입력하거나, 첫 telemetry 로 사후 매칭 — 필요해지면 검토).

## 7. 추가 발견 — hw_id UNIQUE 충돌이 카메라를 영구 오프라인으로 만들던 버그 (우리 쪽, 수정)

### 7.1 무엇이

telemetry 핸들러가 `hw_id` 가 NULL 인 행에 하트비트로 온 hw_id 를 채우는데, 이 UPDATE 가 `last_seen_at`·`is_online` 과 **같은 문장**이었습니다. 같은 owner 의 **다른 활성 행**이 이미 그 hw_id 를 갖고 있으면 `(owner_id, hw_id)` UNIQUE 로 23505 → **하트비트가 통째로 실패** → `last_seen_at` 이 영원히 안 올라 3분 뒤 offline 판정 → 멀쩡히 켜진 카메라가 앱·콘솔에서 **영구 오프라인**. `clip_stats`·`image_state` 도 같이 유실. 실패는 로그에만 남아 조용했고 15초마다 반복됐습니다.

### 7.2 조건 — 정확히 "기존 행을 안 지운 채 재등록"

```
지우고(해제하고) 재등록  → 이전 행이 인덱스에서 빠짐 → 충돌 없음
안 지우고 재등록          → 이전 행이 hw_id 선점 → 새 행의 하트비트 전부 실패 🔴
```

### 7.3 확인 부탁 — 1840·beard "업로드 끊김"이 이건지

업로드 끊김이 실제 오프라인일 수도 있지만, 이 버그면 **카메라는 켜져 있는데 서버만 못 보는** 상태입니다. 판정:

```sql
-- hw_id 가 끝내 안 채워진 활성 행 (구 펌웨어 or 충돌 피해자 후보)
SELECT camera_id, owner_id, name, created_at, last_seen_at
FROM public.cameras
WHERE hw_id IS NULL AND unlinked_at IS NULL
ORDER BY created_at DESC;

-- 그 owner 에 같은 보드로 추정되는 다른 활성 행이 있는지 (이름 접미사로)
SELECT owner_id, name, camera_id, hw_id, unlinked_at
FROM public.cameras
WHERE owner_id IN (<위 결과의 owner_id>)
ORDER BY owner_id, created_at;
```

브리지 로그에서는 수정 전엔 `cameras UPDATE 실패`, 수정 후엔 `hw_id=… 백필 충돌 — 같은 owner 의 활성 행 [...] 이 이미 보유` 로 찍힙니다. 후자가 보이면 **이전 행을 해제**하면 다음 하트비트부터 정상입니다.

### 7.4 수정 (`d923e7b`, 배포됨)

hw_id 백필을 별도 UPDATE 로 분리. 충돌은 23505 로 구분해 **상대 행(camera_id)까지 경고 1회**, 재시도 중단. 하트비트는 충돌과 무관하게 매번 갱신. 카메라·기기 양쪽. 회귀 테스트 추가.

### 9.1 "30분 넘어서 이름을 저장하는 흐름" — 서버에 있었습니다 → 제거

`POST /cameras/pair` 가 **같은 hw_id 행을 재사용할 때 `name` 을 펌웨어가 보낸 값으로 덮어쓰고** 있었습니다.
펌웨어는 프로비저닝 때 받은 이름을 재페어링마다 다시 보내므로, BLE 프로비저닝 기기가 WiFi 를 바꾸려고
30분 뒤에 재페어링하면 사용자가 앱에서 바꾼 이름과 트리거가 붙인 접미사가 함께 지워지고, v3 트리거는
(30분이 지나) 다시 붙이지 않습니다. 베타 기기는 페어링을 호출하지 않아 지금까지 드러나지 않았을 뿐입니다.

→ **재사용 경로에서 `name` 을 더 이상 쓰지 않습니다** (기기 `/devices/pair` 는 `name`·`species` 동일). 이름은
새 행 INSERT 때만 들어가고, 이후 변경은 사용자 `PATCH` 뿐입니다. 즉 이제 서버가 `cameras.name` 을 UPDATE 하는
경로는 **사용자 PATCH 하나**이며, 이건 30분 뒤라면 사용자 의도대로 접미사 없이 남는 게 맞습니다.

앱 쪽 "등록 후 30분 넘어서 처음 저장" 흐름 여부는 앱팀 확인 사항으로 넘기겠습니다.
