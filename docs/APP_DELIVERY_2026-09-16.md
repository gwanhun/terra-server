## §1 — 예약 `payload.brightness` ✅ 그대로 쓰세요

2026-08-12 질문 4("`schedules.payload` 가 `mist` 의 `duration_ms` 외 다른 키도 통과시키는가")의 답은 **통과시킵니다** 입니다.

```jsonc
// POST /devices/{id}/schedules
{ "action": "led_on", "kind": "daily", "time_of_day": "20:00",
  "pair_id": "<uuid>", "payload": { "brightness": 50 } }
```

| 단계 | 동작 |
|---|---|
| POST / PATCH | `payload` 원본 그대로 저장. **`mist` 외에는 검증 안 함** |
| GET | `payload` 그대로 반환 |
| 예약 실행 | `commands.payload` 에 그대로 |
| MQTT 발행 | `led_on` + `brightness` 로 발행 |

- **릴레이 보드는 400 이 아니라 무시입니다.** 서버는 `led_dimmable` 을 확인하지 않고, 릴레이 보드 펌웨어는 `brightness` 를 파싱조차 하지 않고 켜기만 한 뒤 `ok` 를 보냅니다. 기대하신 동작 그대로입니다.
- **⚠️ `brightness: 0` 은 `led_on` 이어도 실제로 꺼집니다**(펌웨어가 `state: "OFF"` 응답). 슬라이더 초기값·복원 로직에서 0 이 새면 "켜기 예약이 실행됐는데 꺼져 있음" 이 됩니다. **하한 20% 를 앱에서 강제해 주세요.** 서버는 막지 않습니다.
- MOSFET 보드는 0~100 으로 조용히 clamp 합니다(하한 없음). 범위 밖이어도 `bad_request` 가 아닙니다.

회귀 테스트를 붙여뒀으니 이 경로가 깨지면 저희 CI 에서 잡힙니다.

## §2 — 예약 `payload.duration_ms`(냉각팬) ✅ 그대로 쓰세요

```jsonc
{ "action": "fan2_on", "kind": "weekly", "time_of_day": "12:00",
  "days_of_week": [6, 7], "payload": { "duration_ms": 1800000 } }
```

**단건 + `duration_ms` 방식으로 진행하세요. pair 로 되돌릴 필요 없습니다.**

- 서버는 §1 과 동일 경로로 그대로 전달합니다.
- 펌웨어가 one-shot 타이머를 걸고 시간 뒤 **자동 OFF** 합니다. `fan_on`(환기팬)도 동일합니다.
- **상한은 2시간**입니다. 초과분은 조용히 잘립니다. 앱의 30분/1시간/2시간은 전부 이내입니다.
- ack 의 `state` 가 **`"TIMER"`** 로 옵니다(`duration_ms` 없이 켜면 `"ON"`). 타이머 적용 여부 표시에 쓸 수 있습니다.
- 타이머 진행 중 `fan2_off` 를 보내면 **예약된 자동 OFF 도 함께 취소**됩니다.
- 자동 OFF 후 `telemetry.fan2` 가 **최대 3초 안에** `OFF` 로 바뀝니다.

## §3 — `led_on` + `duration_ms` ⛔ 미지원 (칩 제거 필요)

**펌웨어가 `duration_ms` 를 읽지 않습니다. 그냥 켜고 `result: "ok"` 를 보냅니다.**

우려하셨던 최악의 케이스가 맞습니다. `bad_request` 도 `unknown` 도 오지 않아서 **앱도 서버도 "시간이 지나도 안 꺼짐" 을 감지할 수 없습니다.** `telemetry.led` 도 계속 `ON` 입니다(자동 OFF 자체가 없으므로).

구조적 이유: 타이머는 릴레이 드라이버의 one-shot 으로 구현돼 있는데 MOSFET 보드의 LED 는 릴레이가 아니라 조광(PWM) 채널이라 **타이머 슬롯이 없습니다.** 펌웨어 전체에서 타이머를 거는 곳은 릴레이 드라이버 한 군데뿐입니다.

**→ 요청서 표의 "1 미지원" 행대로 "자동 시간" 칩을 제거하거나 비활성 + 안내해 주세요.**

참고로 `duration_ms` 를 실제로 처리하는 action 은 **`mist` / `fan_on` / `fan2_on` 셋뿐**입니다.

### 타이머 슬롯 질문에 대한 답

- 슬롯은 **액추에이터별로 독립**입니다(펌프·팬1·팬2 각 1개). 기기당 하나가 아닙니다.
- 팬1 타이머가 도는 중에도 팬2 타이머는 정상적으로 걸립니다.
- 다만 **LED 는 슬롯이 아예 없어서** 이 질문 자체가 성립하지 않습니다.

### LED 타이머를 넣을지 — 결정 부탁드립니다

| 안 | 내용 | 비고 |
|---|---|---|
| A (권장) | 앱이 칩 제거 | 지금 바로 정합. 서버·펌웨어 변경 없음 |
| B | 펌웨어에 LED 타이머 추가 | 근본 해결. 릴레이 보드는 한 줄, MOSFET 보드는 새 타이머 구조 필요 |
| C | 서버가 지연 `led_off` 발행 | 구버전 기기도 커버되나 **권장하지 않음** — 분무 설계 때 의도적으로 배제한 방식(OFF 유실 시 안 꺼짐) |

**B 로 가신다면 두 가지를 정해주세요.**
1. 지원 여부 플래그 이름 (예: `capabilities.led_timer`) — 구버전 기기가 남으므로 앱 분기가 필요합니다
2. 상한 — **앱의 3시간(10,800,000ms)은 팬 상한 2시간을 넘습니다.** 3시간을 살리려면 펌웨어 상수를 같이 올려야 합니다

## §6 — 과거 온습도: 지표별 유효 표본 수 제공 시작 ✅

요청하신 "정확한 일평균을 위한 유효 표본 수" 입니다. **`telemetry_30m` 에 컬럼 4개를 추가하고 배포했습니다.**

```jsonc
// 조회 예시
sb.from('telemetry_30m')
  .select('bucket, t_a_avg, t_a_min, t_a_max, h_a_avg, sample_count, t_a_count, h_a_count')
```

| 컬럼 | 의미 |
|---|---|
| `sample_count` | 버킷 내 **원본 행 수**. **지표별 유효 표본 수가 아닙니다** |
| `t_a_count` / `h_a_count` | A센서 온도·습도의 **유효 표본 수** (센서 정상 보고분만) |
| `t_b_count` / `h_b_count` | B센서 온도·습도의 유효 표본 수 |

**가중평균은 `sample_count` 가 아니라 지표별 `*_count` 를 가중치로 쓰세요.**
요청하신 예시대로 `(20×1 + 30×3) / 4 = 27.5` 가 나오려면 그래야 합니다. 온도 센서만 죽어도 `sample_count` 는 그대로이기 때문입니다.

### ⚠️ 세 가지 주의

1. **소급 불가.** 원본이 7일만 보존되므로 **2026-09-15 이전 버킷의 `*_count` 는 `null`** 입니다. 요청서 방침대로 `--` 로 처리해 주세요.
2. **센서 고장 값이 이제 제외됩니다.** 예전에는 고장 보고 시의 무의미한 값이 평균·최소·최대에 섞여 들어갔습니다. **즉 보조(B) 센서 평균처럼 지금까지 "그럴듯한 숫자" 로 보이던 값이 실제로는 가짜였을 수 있습니다.** 배포 후 실측에서 운영 중인 기기 4대 모두 B센서 유효 표본이 0 이고 `t_b_avg` 가 `null` 로 나옵니다. B센서를 화면에 쓰신다면 `null` 처리를 확인해 주세요.
3. **일 단위로 묶을 때 타임존 주의.** 버킷 경계는 **UTC 기준** 정시/30분입니다. KST 일평균을 만들려면 `bucket + 9h` 로 날짜를 만든 뒤 묶어야 합니다. 그대로 날짜를 자르면 9시간 어긋납니다.

`docs/APP_TIMESERIES_CHART.md` 의 "`sample_count < 300` 이면 부분 데이터" 규약은 위 1번 때문에 아직 정확하지 않습니다. 새 컬럼이 충분히 쌓인 뒤 지표별 기준으로 바꾸는 걸 권합니다.

## §7 — ⛔ 히터 UI 를 노출하지 마세요

서버는 `heater_on` / `heater_off` 를 예약 허용 목록에 두고 있지만, **두 보드 모두 펌웨어에서 히터가 미구현**입니다(핸들 NULL). 명령을 보내면 **항상 `unknown_action`** 이 돌아옵니다.

- 문서에 있는 `locked`(히터 안전잠금) result 는 **도달 불가**입니다
- 앱에서 히터 예약을 만들 수 있으면 사용자는 100% 실패하는 예약을 갖게 됩니다
- 서버 허용 목록은 향후 히터 하드웨어를 위해 남겨둡니다. **서버에서 400 으로 막아드릴까요?** 원하시면 알려주세요

## §8 — 냉각팬 UI 노출 조건 ⚠️

**릴레이 보드에는 `fan2_*` 명령 코드 자체가 없습니다.** 보내면 `unknown_action` 입니다.
서버는 `fan2_*` 예약 생성을 허용하므로 **예약은 만들어지고 실행만 실패**합니다.

→ 이미 전달드린 계약대로 **`telemetry.fan2 != null`** 로 노출 여부를 판별해 주세요(`docs/APP_FAN2_2026-09-07.md` §4).

### 덧붙여: `busy` / `error` 문구

`busy` 는 두 원인에서 나오고 구분되지 않습니다.
- 같은 액추에이터에 **이미 타이머가 걸려 있는데** 또 타이머 명령
- **직전 명령 후 200ms 이내** (최소 토글 간격 가드)

게다가 같은 200ms 가드 위반이 **비타이머 명령(`fan_off`, `led_*`, `relay_on` 등)에서는 `error`** 로 나옵니다.
→ 둘 다 "잠시 후 다시 시도" 계열로 묶는 게 안전합니다.

### 재시도는 새 명령으로

펌웨어가 최근 `msg_id` 8개를 기억해 중복을 거르는데, **`busy`·`error` 로 거절된 명령도 기억합니다.**
같은 `msg_id` 로 재시도하면 `duplicate` 만 돌아옵니다. **재시도는 `commands` 에 새 행을 넣어 새 `msg_id` 로** 보내세요.

## §9 — ⚠️ 기기 삭제는 "등록 해제" 가 아닙니다 (★★)

재설계 요청서의 "삭제 = 등록 해제 및 그룹 연결 해제이며 R2 원본이나 과거 통계 원본을 삭제하는 기능이 아니다" 와 **현재 서버 구현이 정반대**입니다.

`DELETE /devices/{id}` 는 hard delete 이고 아래가 **전부 함께 삭제**됩니다.

```
device_settings · telemetry · telemetry_1m · telemetry_30m(장기 통계)
commands · alerts · schedules
```

`DELETE /cameras/{id}` 는 **`motion_clips` 행 전체**를 삭제합니다. R2 파일은 남지만 DB 행이 없어져 접근 경로가 끊깁니다.

**→ 기록 보존이 필요한 해제 동작에 이 엔드포인트를 쓰면 안 됩니다.** 소프트 해제는 미구현이며, 저희 작업 우선순위 1번입니다. API 동작이 바뀌므로 **합의 후 진행**하겠습니다.

### ✅ 좋은 소식 두 가지

- **영상 소유권 격리는 이미 요구대로입니다.** 클립 소유자는 촬영 시점에 행에 박히고 카메라 소유자를 따라가지 않습니다. 카메라를 다른 계정에 재등록해도 이전 주인의 과거 영상이 새 주인에게 보이지 않습니다.
- **그룹 삭제는 안전합니다.** 구성원은 보존되고 연결만 끊깁니다(연쇄 삭제 아님). 다만 과거 클립의 그룹 귀속은 사라지므로, 설계 중인 이력 테이블이 그 손실을 메워야 합니다.

### ⚠️ 소유권 이전을 만든다면

`telemetry` 계열에는 소유자 컬럼이 없고 기기 소유자를 따라갑니다. **소유권을 넘기면 과거 센서 기록 전체가 새 소유자에게 그대로 보입니다.** 이전 기능을 설계하실 때 이 부분을 같이 봐주세요.

## §10 — 푸시 이벤트: 서버 준비 완료 🔧

요청하신 연동의 **서버측 구조를 만들어 배포했습니다.** 아직 켜지 않았습니다.

- 명령 ACK 가 확정되면 전송 대기열에 적재하고, 워커가 5초 주기로 Edge Function 에 POST 합니다.
- 네트워크 오류·5xx 는 지수 백오프로 재시도하고, **4xx 는 요청서대로 무한 재시도하지 않습니다.**
- 재시도는 최초와 **동일한 `event_id`** 로 나갑니다.
- 발행 범위는 요청서대로 **예약(`schedule`)·가드(`guard`)만**입니다. 즉시 제어는 제외했습니다.
- secret 은 서버 환경변수에만 두며 **본문·로그에 들어가지 않습니다.** 헤더로만 나갑니다.

**`PUSH_EVENT_INGEST_SECRET` 을 안전한 채널로 주시면 그 즉시 켤 수 있습니다.** 값이 없으면 워커가 시작조차 하지 않습니다.

### ⛔ `device.action.ended` 는 현재 관측 불가

서버에 명령의 시작/종료 개념이 없고, **지속시간 명령의 자동 OFF 는 펌웨어 내부 타이머라 종료 ACK 가 오지 않습니다.** 진짜 종료를 낼 수 있는 건 **구간 예약의 off 명령 ACK** 뿐입니다.

| 안 | 내용 | 정확도 |
|---|---|---|
| A (권장) | `ended` 를 구간 예약에만 한정 | 정확. 추가 작업 없음 |
| B | `acked_at + duration_ms` 로 지연 이벤트 신설 | 추정치(조기 종료·실패 반영 못 함) |
| C | telemetry 상태 전이 감지 | 실측이나 15초 지연·유실 가능 |

### payload 필드 조정 제안

| 요청서 필드 | 서버 원천 | 비고 |
|---|---|---|
| `user_id` | `commands.issued_by` | NULL 이면 `devices.owner_id` 폴백 |
| `schedule_id` | `commands.source_id` | `schedule_id` 라는 컬럼은 없습니다 |
| `device_id` | UUID | **`device_key`(`terra-xxxxxxxx`)를 함께 싣겠습니다** — 요청서 예시가 TEXT 인데 `enclosure_id` 는 UUID 라 혼재를 피하려고 |
| `result` | 펌웨어 원문 | 판정값은 **`outcome`**(`succeeded`/`failed`)로 분리 — `result` 는 이미 다른 어휘의 컬럼이라 |

### ⚠️ 성공/실패 판정 기준이 다릅니다

서버는 응답 내용과 무관하게 **`status` 를 항상 `acked`** 로 적습니다. **실패는 `status` 가 아니라 `result` 문자열로 갈라야 합니다.** 저희는 `result == "ok"` 만 성공으로 보고 나머지를 실패로 묶습니다.

### ⚠️ `execution_source` 의 `timer` 정의가 필요합니다

서버의 `commands.source` 값은 `manual` / `schedule` / `guard` 가 실사용이고 **`timer` 는 한 번도 쓰인 적이 없습니다.** 지속시간이 붙은 즉시 제어는 `manual` 로 들어옵니다. `timer` 로 무엇을 지칭하시는지 알려주세요.
