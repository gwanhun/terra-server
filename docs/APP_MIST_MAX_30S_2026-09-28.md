# 앱 전달 — 분무 상한 30초 펌웨어 + 분무 시간 자유 설정(1~20초): 10초는 분할 없이

> **대상**: 앱 개발 담당
> **작성**: terra-server 백엔드 담당, 2026-09-28
> **성격**: 9/23 회신([BACKEND_HANDOFF_REPLY_MIST_DURATION_2026-09-23.md](BACKEND_HANDOFF_REPLY_MIST_DURATION_2026-09-23.md))에서 "보류"했던 **펌웨어 상한 상향**을 이번 리플래시에 포함했고, 서버의 `duration_ms` **화이트리스트를 폐지**해 1000~20000 범위의 어떤 정수든 받습니다. 필수 작업은 없고(기존 5·10초 칩 그대로 유효), **20초 칩이나 슬라이더 추가는 선택**입니다.
> **관련 커밋**: 펌웨어 nano `a09772f` / supermini `7ed013d`. 서버: 화이트리스트 폐지(이번 커밋), 문서 `291930c`.

## 1. 무엇이 바뀌었나

| | 구 펌웨어 (~9/28) | 신 펌웨어 (9/28+) |
|---|---|---|
| 펌웨어 분무 1회 상한 | 5초 (`MIST_MAX_MS 5000`) | **30초** |
| `capabilities.mist_max_ms` 보고 | 없음 → 서버가 5000 으로 간주 | **30000** — 페어링 body 와 3초 telemetry 양쪽에 실림. 재페어링 없이 첫 telemetry 에서 서버 DB 갱신 |
| 앱이 10초 분무 요청 시 | 서버가 5초 + 5초로 분할 (총 ~12초, 중간 2초 쉼) | **한 번에 10초** 연속 분사 |
| `commands` 행 | 원 명령 1 + 후속 `source='timer'` 1 | **원 명령 1 만** |
| 5초 분무 | 한 번에 | 한 번에 (변화 없음) |

- 30초는 서버 이상값·침수 방지용 펌웨어 최후 방어선이지, 앱이 30초를 보낼 수 있다는 뜻이 아닙니다(보내면 400).

### 1.1 `duration_ms` 화이트리스트 폐지 → 1000~20000 범위 정수 (서버, 2026-09-28)

지금까지 1/2/3/5/7/10초만 받던 검증을 **범위 검사**로 바꿨습니다. **1000 이상 20000 이하의 정수(ms)** 면 어떤 값이든 됩니다(예: 4000, 13500). REST `POST /devices/{id}/mist` 와 예약(`POST /schedules`)이 같은 검증을 쓰고, `commands` 직접 INSERT 는 원래 서버 검증이 없었습니다. 범위 밖(예: 500, 25000)이나 정수가 아니면 400.

| 기기 | 임의 값(예: 13초) 요청 시 |
|---|---|
| 신 펌웨어 (`mist_max_ms` 30000) | **한 번에 13초** 연속 분사, `commands` 1행 |
| 구 펌웨어 (미보고 = 5000) | 5초 단위 분할: 5 + 5 + 3. 원 명령 1행 + `source='timer'` 후속 2행(8000 → 3000 으로 발행 시마다 재분할). 분할 사이 약 2초 쉼 |

- **구 펌웨어 기기도 안전합니다.** 서버가 5초 단위로 자르고 분사마다 펌웨어 타이머가 끄므로, 후속이 유실돼도 "물이 덜 나옴"일 뿐 펌프가 켜진 채 남지 않습니다. 펌웨어가 5초 넘는 값을 직접 받아도 5초로 clamp 합니다.
- 버튼 잠금은 기존 규칙(**총 분사 시간 + 3초**) 그대로. 구 펌웨어는 분할 쉼만큼 더 걸리지만 잠금 중 재요청은 펌웨어가 `busy` 로 거절합니다.
- 칩 노출을 기기별로 나눌 필요 없습니다. 20초 상한은 서버 정책값이라 나중에 올리면 앱은 그대로 됩니다.
- 분할 로직은 서버에 그대로 남아 있습니다. 구 펌웨어 기기는 계속 분할되고, 기기별로 자동 판단됩니다. 리플래시 순서와 무관하게 앱 동작은 같습니다.

## 2. 앱에서 확인할 것 (선택)

1. 명령 이력이 `source='timer'` 후속 행의 존재를 전제로 하는 표시(예: "2회 분사")가 있다면, 신 펌웨어 기기에서는 1행만 오는 것이 정상입니다.
2. 버튼 잠금은 9/23 규칙(총 분사 시간 + 3초) 그대로 두면 됩니다. 신 펌웨어에서는 3초 여유가 조금 남지만 문제 없습니다.
3. 예약(schedule)의 10초 분무도 동일하게 한 번에 나갑니다.
